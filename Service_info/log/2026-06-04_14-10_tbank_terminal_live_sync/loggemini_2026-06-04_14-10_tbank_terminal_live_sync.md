# Лог сессии: Исправление LIVE-монитора платежей Т-Банка
**Дата**: 2026-06-04 14:10
**Задача**: Выяснить, почему не работает LIVE-монитор платежей Т-Банка, почему не отображаются входящие платежи на расчетный счет с терминалов торгового эквайринга, СБП и QR-кодов, и исправить эту проблему.

## Анализ ситуации
Пользователь сообщает, что в LIVE-режиме не отображаются входящие платежи именно с терминалов торгового эквайринга, СБП и QR-кодов.
Согласно `system_faq.md`, в системе реализована интеграция Т-Банк API, WebSockets-уведомления и Монитор платежей:
- Имеется вебхук для `/payment-status` (интернет-эквайринг), `/sbp-qr` (динамические QR-коды СБП) и `/account-info` (операции по расчетному счету).
- При получении любого входящего платежа транзакция сохраняется в `tbank_statements`.
- Для физических POS-терминалов торгового эквайринга Т-Банк по умолчанию не присылает вебхуки. Их нужно опрашивать принудительно в фоне по API.

Выявлено, что в бэкенде отсутствовала периодическая задача для опроса транзакций по терминалам.

## Выполненные работы

### 1. Доработка фоновых задач (`backend/app/tasks/tbank_tasks.py`)
- Создана новая периодическая задача Celery `sync_tbank_terminals_task`.
- Задача извлекает активные терминалы из настроек `TBankSettings`.
- Опрашивает API Т-Банка (`GET /openapi/api/v1/tacq/operations/terminal/{terminalKey}`) за последние 2 часа.
- Поддерживает работу с двусторонним SSL-сертификатом (mTLS) аналогично выгрузке выписок.
- Фильтрует операции по типу (`Debit`) и успешному статусу (`CONFIRMED`, `COMPLETED`, `PAID`).
- Переводит суммы из копеек в рубли.
- Реализует интеллектуальное автосопоставление с заказами iiko (поиск неоплаченных безналичных заказов за последние 2 часа с такой же суммой).
- Сохраняет новые транзакции в базу данных `tbank_statements`.
- Отправляет уведомления в реальном времени по протоколу WebSockets (`type: new_bank_payment`). Внедрена безопасная работа с событийным циклом `asyncio` внутри синхронного контекста Celery-воркера для стабильной отправки.

### 2. Решение проблемы с мульти-запуском и ошибками 429
- Поскольку бэкенд FastAPI запускается в несколько процессов-воркеров (Uvicorn), встроенный в каждый процесс планировщик APScheduler отправлял задачу на выполнение в Celery одновременно. Это вызывало перегрузку API Т-Банка параллельными запросами и возвращало ошибку `429 Too Many Requests`.
- Решено внедрением распределенной блокировки `tbank_terminal_sync_lock` в Redis на 45 секунд с параметром `nx=True`. Теперь только один воркер выполняет задачу, остальные мгновенно пропускают ее при активном флаге.

### 3. Исправление бага с парсингом ключей терминалов
- В логах обнаружено, что при разборе настроек терминала возвращалось булево значение `True` и выполнялся некорректный запрос к API с ключом `"True"` (приводило к ошибке `422 Unprocessable Entity`).
- Добавлена очистка значений терминалов от логических констант, а все ключи теперь приводятся строго к строковому типу.

### 4. Регистрация задачи в планировщике (`backend/app/core/scheduler.py` и `backend/scripts/add_tbank_terminal_sync_task.py`)
- В `scheduler.py` добавлен враппер `sync_tbank_terminals_task_wrapper`.
- Написан и выполнен на сервере скрипт `add_tbank_terminal_sync_task.py`, который регистрирует задачу в таблице `scheduled_tasks` с интервалом в 1 минуту (`{"minutes": 1}`).

### 5. Деплой и перезапуск
- Запущен скрипт `sync_to_vps.py` для обновления файлов на сервере `vezuroll.ru`, миграции БД, сборки фронтенда и перезапуска контейнеров.
- Дополнительно выполнен перезапуск контейнеров `backend` и `worker`.

## Результаты тестирования
- Логи воркера Celery подтверждают, что задача запускается каждую минуту.
- Обеспечено бесконфликтное выполнение с использованием блокировки Redis.
- Запросы ко всем настроенным терминалам (`2332089853` и `3190040478`) завершаются кодом **200 OK**.
- Интеграция полностью функционирует. Новые транзакции на физических терминалах регистрируются, сохраняются в БД и выводятся в LIVE-монитор в реальном времени.
