## Инфраструктура фоновых задач (Celery)

Для выполнения длительных операций (массовая синхронизация, импорт из файлов, рассылки) используется **Celery** с **Redis** в качестве брокера сообщений.

### Компоненты:

- **Broker**: `redis://redis:6379/0` (контейнер `foodtech-redis`)
- **Worker**: Отдельный Docker-контейнер `foodtech-worker`, запускающий `celery -A app.core.celery_app worker`.
- **App**: Конфигурация находится в `backend/app/core/celery_app.py`.
- **Задачи**: Определены в `backend/app/tasks/customer_tasks.py`.

## Интеграция с iiko (OLAP)

Для синхронизации доставок и выручки курьеров используются OLAP-отчеты iiko Server (Resto API).

### Основные поля для отчета DELIVERIES:

- **Тип отчета**: `DELIVERIES`
- **Обязательный фильтр**: `OpenDate.Typed` (Учетный день)
- **Группировка (groupByRowFields)**:
  - `Delivery.Number` — Номер доставки
  - `Delivery.Courier` — ФИО курьера
  - `Delivery.Street` — Улица
  - `Delivery.Region` / `Delivery.Zone` — Зона доставки
- **Агрегация (aggregateFields)**:
  - `fullSum` — Полная сумма заказа
  - `UniqOrderId` — Уникальный ID заказа (обязательно для предотвращения 422 ошибки)

### 6. Защита статуса «Высокий риск» (Обновлено: 29.04.2026)

Исправлена проблема потери статуса «Высокий риск» при синхронизации:

- **Решение**: В `iiko_sync_service.py` добавлена проверка. Если поле риска отсутствует в ответе iiko, локальный статус в базе данных **сохраняется**.
- **Доп. проверка**: Статус риска также определяется по наличию слов "риск" или "risk" в категориях лояльности гостя в iiko.

- **Вкладка "Бонусы"**: Отображает текущий баланс кошельков и полную историю транзакций.

  - **Структура данных (Обновлено 30.04.2026)**: API возвращает список объектов `AddressHistoryResponse` (City, Settlement, Street, House, Entrance, Floor, Apartment, Doorphone).
  - **Маппинг**: Фронтенд отображает эти данные в виде тегов (chips) для удобного чтения.
- **История Заказов (12 мес)**: Загрузка истории доставок из iiko Cloud с возможностью просмотра деталей.

### 25. Fallback-синхронизация по ID и Телефону [NEW 29.04.2026]

Реализована отказоустойчивая схема поиска гостя в iiko Cloud для предотвращения ошибок "Customer not found" и работы с устаревшими ID:

- **Логика поиска (iiko_sync_service.py)**:
  1. Если в локальной БД у клиента уже есть `iiko_customer_id`, система первым делом пытается получить данные из iiko по этому ID.
  2. Если поиск по ID возвращает ошибку (например, клиент был удален или перенесен в iiko) или ID отсутствует, система автоматически переключается на поиск по **номеру телефона**.
  3. Это гарантирует, что профиль клиента будет синхронизирован, даже если его внутренний идентификатор в iiko изменился.
- **Интеграция с API (customers.py)**:
  - Эндпоинт `/api/v1/customers/by-phone/{phone}` теперь автоматически инициирует синхронизацию с iiko, если клиент не найден в локальной базе. Это обеспечивает мгновенное появление данных гостя при открытии его первого заказа в админ-панели.
- **Техническая реализация**:
  - Метод `get_customer_info` в `iiko_service.py` расширен для поддержки параметров `customer_id` and `phone`.
  - В случае ошибки 400 (неверный ID/телефон) метод возвращает структурированный ответ `found: False`, что позволяет бизнес-логике корректно обрабатывать отсутствие данных без генерации лишних исключений.

- **Оптимизация пула соединений (database.py)**:
  - Для поддержки стабильной работы при синхронной синхронизации во время создания заказа лимиты пула увеличены: `pool_size=20`, `max_overflow=40`.
  - Установлен `pool_timeout=60` для исключения ошибок "QueuePool limit overflow" (белый экран в админке).

### Автоматическое определение URL (Dynamic URL Discovery)

В системе реализована "умная" логика определения публичного адреса для регистрации вебхуков iiko Cloud. Это позволяет сайту автоматически адаптироваться при смене домена.

- Автоматически обновляет поле `webhook_url` в базе данных.

## Управление доступом (RBAC) [Обновлено 01.05.2026]

В системе реализована гибкая модель управления правами доступа на основе ролей.

### Ключевые компоненты:

- **Роли (Roles)**: Группы прав. Могут быть системными (неудаляемыми) и пользовательскими.
- **Права (Permissions)**: Атомарные права доступа (например, `users_manage`, `orders_view`).
- **RolePermissionLink**: Таблица связей "многие-ко-многим" между ролями и правами.

### Расположение файлов:

- **Модели**: `backend/app/models/role.py`
- **Схемы**: `backend/app/schemas/user.py` (добавлены `RoleCreate`, `RoleUpdate`, `RolePermissionUpdate`)
- **API**: `backend/app/api/users.py` (CRUD для ролей и управление правами)
- **Фронтенд**:
  - `admin/resources/js/pages/users.vue` (основная страница с вкладками)
  - `admin/resources/js/views/pages/users/UserList.vue` (компонент списка пользователей)
  - `admin/resources/js/views/pages/users/RoleList.vue` (компонент управления ролями и правами)

### API Эндпоинты:

- `GET /api/v1/users/roles` — список ролей с вложенными правами.
- `POST /api/v1/users/roles/{id}/permissions` — обновление набора прав для конкретной роли.

### Защита API (Backend):

Для защиты эндпоинтов используется зависимость `require_permission(permission_code)`.
Пример: `Depends(require_permission("users_view"))`.
Суперпользователи (`is_superuser=True`) имеют доступ ко всем ресурсам в обход проверок.
